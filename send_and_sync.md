# Send куда? Sync кого?

Borrow checker и правила алиасинга -- как статические, так и динамические -- это все, конечно, здорово, но для успешного решения прикладных задач и одновременно обеспечения безопасности памяти этого достаточно лишь в однопоточном мире. Как только потоков становится больше одного и возникает желание и необходимость:
- менять данные в одном и читать в другом
- менять их одновременно из двух потоков

Так сразу же ограничение *у вас не может быть одновременно двух &mut ссылок* или *у вас не может быть одномременно &mut и & ссылки* на один и тот же объект приходит и бьет по рукам *настоящих* инженеров на *настоящих* языках программирования. После чего они говорят, что на safe Rust нельзя сделать ничего полезного, и уходят дальше программировать на C и C++.

Действительно, просто так, с одними лишь примитивными типами и без unsafe тут далеко не уедешь. Потому стандартная библиотека Rust предоставляет многообразие не совсем примитивных типов, прячущих внутри себя `unsafe {}` и обещающих, что там все правильно. А со стороны их safe интерфейсов идея очень проста:

> Хорошо, нам статически запретили иметь одновременно больше одной уникальной `&mut` --- давайте тогда использовать для доступа *и модификации* разделяемые `&` ссылки. Их же можно делать сколько угодно, пока они указывают на валидный живой объект. 

Если  объект типа `T` (его внутреннее состояние) можно как-то изменить, имея доступ к нему через `&T` ссылку -- говорят, что тип `T` обладает свойствами **interior mutability**. И у всех таких типов глубоко внутри сидит `unsafe {}`. И это нормально. 

Пример такого типа из стандартной библиотеки -- `Cell<T>` -- ячейка памяти, хранящая `T`, которую можно изменять через `&Cell<T>` ссылки.

Если обмазать все подряд с помощью `Cell<T>`, можно в **однопоточных** программах практически никогда не захватывать ни одной `&mut T` ссылки и не страдать с borrow checkerом! [^1]

И смотрите какая штука: 
- Вот было и есть статически проверяемое ограничение -- уникальность `&mut` ссылки. Из него автоматически, естественным образом получалась защита от гонок данных в многопоточном коде: не выйдет одновременно писать из двух потоков, или читать и писать в одну и ту же переменную, ведь мутабельная ссылка лишь одна! 
- А теперь у нас появились типы c *interior mutability*, `&mut` больше не нужен, мы все будем делать через `&` -- существующая статическая проверка больше не защищает от гонок данных. Нужна новая проверка.

Здесь начинается наша история.


**А зачем нам Sync?**

В очень многих языках программирования потокобезопасность типов и функций обозначается одним едиственным способом -- ну, в документации написано, значит, безопасно. Не самый надежный способ.
В некоторых языках потокобезопасность вшита намертво: например, через глобальный мьютекс (GIL, Global Interpreter Lock) в Python, который оттуда очень долго пытались убрать.
В других языках бывают синтаксические конструкции, чтоб пометить методы классов, чтоб при их вызове всегда захватывалась ассоциированная с объектом блокировка: например, `synchronized` в Java.

В Rust пошли хитрым и довольно простым путем. Этим же путем, кстати, мог бы и пойти C++:
В языке же есть типажи (traits) -- давайте с их помощью просто наложим ограничение, что безопасно может взаимодействовать с разными потоками, а что не может. Вопрос лишь в том, а что мы имеем в виду под взаимодействием.

Если прыгнуть в документацию Rust, RustBook, Rustonomicon и прочая, на нас сразу вывалят `Sync`, `Send`, какие они вместе разные и оба важные, и вот как их понять,  и надо быть осторожными, потому они `unsafe`, полагайтесь на компилятор, бла-бла-бла...

Давайте не будем туда прыгать. Я сейчас вас буду убеждать, что мы можем в принципе построить свою собственную систему безопасного взаимодействия с потоками. И ее можно даже засунуть в C++ [^2].

Потоки не берутся из ниоткуда. Ваше userspace[^3] приложение всегда стартует с одним, main, потоком. И в процессе своей жизнидеятельности просит у операционной системы: а создай-ка мне новый поток. 

Среднеуровневый интерфейс для этого предоставляет, например, библиотека posix-threads [^4]:
```C
       int pthread_create(pthread_t *restrict thread,
                          const pthread_attr_t *restrict attr,
                          typeof(void *(void *)) *start_routine,
                          void *restrict arg);
```

Первые два аргумента мы можем сейчас проигнорировать, а вот `start_routine` и `arg` -- то, с чем будем работать.

Указатель на функцию -- какой код начать исполнять. И с каким агрументом -- все просто. Аргумент один, передается по ссылке (указателю), и имеет непрозрачный тип `void`. `start_routine` должна сама знать и разобраться, что туда ей передали, выполнив преобразование типов указателей.

И больше для передачи данных между новым потоком и старым ничего нет [^5]. Организуйте сами что хотите с помощью этих `void* arg`;

Интерфейс, конечно, не самый удобный. Потому и среднеуровневый. Над ним можно и стоит построить более удобную абстракцию. Вернемся для этого в Rust.

Упрощенный вариант в Rust может быть таким:

```Rust
// пока unsafe
unsafe fn thread_create<T>(start_routine: fn(T), arg: T) {
    // мы передадим владение T новому потоку -- отправим в него arg
    // чтоб указатели не протухли, пока поток еще не стартовал -- аргументы уходят в heap
    let box_arg = Box::new((arg, start_routine));
    let raw_arg = Box::into_raw(box_arg);
    pthread_crate(..., 
        |raw_arg: *mut c_void| {
            // забираем владение
            let (arg, f) = * unsafe { Box::from_raw(raw_arg as *mut (T, fn(T))) };
            f(arg);
        },
        (&raw mut raw_arg) as *mut c_void
    );

}
```

`ptread_create` принимает аргументы по ссылке. Эта же обертка универсальная: хотим передать владение -- передаем по значению. Хотим передать по ссылке -- просто передадим `&U` в качестве `T`. Разумеется тут сразу же вылезают вопросы о валидности ссылки и ее времени жизни. Пока мы их проигнорируем: в стандартной библиотеке Rust есть `thread::spawn` для случаев без ссылок (или только `'static` ссылок) и `thread::scope` для случаев с ссылками на временные объекты в текущей области видимости. А это `unsafe` вариант, который можно использовать для их реализации.

И теперь, имея набросок высокоуровневого интерфейса, вернемся к тому, что мы хотели:

Единственная операция, которую мы выполняем над аргументом `T` при создании нового потока -- передача его туда. Все. Ничего больше. Так давайте введем типаж `Send`:

```Rust
unsafe trait Send {}
```

И всякий тип, его реализующий, обязуется быть безопасным для передачи в другой поток.

И если мы теперь глянем на безопасный интерфейс `std::thread::spawn` и `std::thread::Scope::spawn`

```Rust
pub fn spawn<F, T>(f: F) -> JoinHandle<T> where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,


pub fn spawn<F, T>(&'scope self, f: F) -> ScopedJoinHandle<'scope, T>
where
    F: FnOnce() -> T + Send + 'scope,
    T: Send + 'scope,    
```

То именно такой `Send` мы здесь и увидим. Безо всяких `Sync`.
А дальше все просто: берем и про **каждый** (`T` или `&U` или `&mut U`) тип думаем, безопасно ли объекты этого типа отправлять в другой поток или нет. И если безопасно, то делаем `unsafe impl Send for ThisType {}` или `unsafe impl Send for &ThatType {}` или `unsafe impl Send for &mut AnotherType {}`
Все. Проблема решена -- новая статическая проверка придумана. Вручную проверим и определимся для примитивных типов, а дальше нужно лишь придумать консервативные правила, как автоматически определять для составных типов, чтоб пользователям языка не приходилось каждый раз думать и писать `unsafe impl Send for MyType {}` или `unsafe impl Send for &MyType {}`. Очевидное консервативное правило, которому следует Rust: если все поля в `struct` или `enum` являются `Send`, то и вся структура тоже `Send`. Всю эту автоматику можно при желании повторить вручную и написать процедурный `derive(Send)` макрос.

И то же самое можно построить, например, в C++. 
Введем

```C++
template <class T>
struct is_send: std::false_type {}

template <class T>
concept Send = is_send<T>::value;

// и определяем для конкретных типов
struct is_send<std::string>: std::true_type {};
```

А зачем же тогда нужен `Sync`, если одного `Send` достаточно? [^6]

А что значит объект безопасно передать в другой поток?

Если объект это что-то владеющее данными, или ресурсом, и только, то все просто
- Можно ли освободить ресурс в другом потоке или в каком потоке память выделяли, туда и обращайтесь?

Например, совершенно не важно какой поток деаллоцирует память[^7] под строку или вектор -- оригинально создавший или последний владелец. Так что `String: Send` и `Vec<T>: Send <=> T:Send`.
Или наоборот, `MutexLockGuard` где создали, там и должны освободить. Нельзя освобождать блокировку из другого потока.
Еще пример -- **не атомарный** счетчик ссылок: `Rc<T>` -- нельзя его в другой поток отправлять, потому что при освобождении он попытается уменьшить счетчик ссылок **не атомарно** и создаст возможность для гонки данных.


А если объект ресурсом не владеет? Что если это ссылка? 

Для уникальной `&mut` доступ гарантированно уникальный. Все здорово. `&mut T` всегда `Send`, да? Нет. 
Это не очевидно, ведь `&mut` зовется уникальным заимствованием, но с ее помощью вообще-то можно очень легко передать владение:

```rust
fn foo<T: Default>(x: &mut T) {
    // забрали владение оригинальным объектом. 
    // Теперь он будет освобожден тут, в другом потоке, а не в исходном
    let local = std::mem::replace(x, T::default());
}
```

Так что `&mut T : Send <=> T: Send`.

А что с неуникальными ссылками? Вокруг них было выстроено все безобразие, чтоб обойти ограничение borrow checker-а через введение interior mutability. Ради них все затевалось же. Давайте скажем, что `&T: Send` <=> вся та interior mutability внутри `T` организована правильно, безопасно, доступ через `&T` гарантировано *синхронизирован*. Ну то есть тип `T` обладает еще одним непроверяемым свойством, в которое нужно поверить, что оно обеспечено автором. Введем для него достойный типаж и название

```Rust
unsafe trait Sync {}
``` 
И скажем, что
```Rust
unsafe impl <T> Send for &T where T: Sync {}
```

Вот и все. Ну и, просто, думать о свойствах типа `T` чуть проще и понятнее, чем заботится о свойствах ссылок на объекты такого типа -- то есть о совсем другом типе `&T`.

Например, очень легко можно сказать, что `String : Sync` -- потому что никакой interior mutability в строке нет. Для любых изменений нужна `&mut String`. А `Cell<T>` естественным образом не `Sync` -- ведь через `&Cell<T>` ее содержимое можно поменять как угодно, а синхронизации между потоками не приложено.

Прекрасно, вот я все это тут разложил. А зачем? Ну ведь очевидно же. Простые истины. Не открыл же ничего нового.

А затем, чтоб показать небольшой пример:

```Rust
// Обертка, разрешающая только уникальный доступ к объекту
#[derive(Debug)]
pub struct NoSharedAccess<T>(T);

impl<T> NoSharedAccess<T> {
    pub fn new(x: T) -> Self { Self(x) }
    pub fn get_mut(&mut self) -> &mut T { &mut self.0 }
}

// Очевидно, что отправлять обертку целиком в другой поток можно только если
// и сам объект безопасно туда отправлять. Компилятор выведет это автоматически
// unsafe impl <T: Send> Send for NoSharedAccess<T> {}

// Раз &T получить из &NoSharedAccess<T> нельзя, то он может быть всегда Sync.
unsafe impl<T> Sync for NoSharedAccess<T> {}
```

Внимание, вопрос: все ли корректно?

Предлагаю помедитировать над таким [вариантом](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&gist=f7209f6195a8bd7add69f84723adf3a0):


```Rust

struct Evil(Rc<i32>);


impl Debug for Evil {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> Result<(), std::fmt::Error> {
        let x = self.0.clone();
        Debug::fmt(&x, f);
    }
}


fn main() {
    
    let evil = NoSharedAccess(Evil(Rc::new(42)));
    
    let evil_ref = &evil;
    use std::fmt::Write;
    std::thread::scope(move |s| {
        s.spawn(move || {
            let mut buffer = String::new();
            for _ in 0..1000 {
                let _ = writeln!(&mut buffer, "{evil_ref:?}");
            }
            println!("{}", buffer.len());
        });
        s.spawn(move || {
            let mut buffer = String::new();
            for _ in 0..1000 {
                let _ = writeln!(&mut buffer, "{evil_ref:?}");
            }
            println!("{}", buffer.len());
        });
    })
    
}
```

Для `NoSharedAccess<T>` `Debug` нельзя автоматически имплементировать без наложения ограничения на `T`. `T` обязан быть `Sync` для него, поскольку `Debug::fmt` берет ссылку `&T`.
