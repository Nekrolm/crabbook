# Как понять Pin, Unpin, !Unpin и не сойти с ума

Есть в Rust одна самая запутанная и переусложненная тема, которая
- С одной стороны особо и не нужна рядовому API-склеивателю
- С другой стороны очень важна при разработке своих примитивов, ffi и низкоуровневой реализации асинхронщины.

`std::pin::Pin`! Будь он не ладен! Вот тут надо Future-объект запинить, иначе не скомпилируется, а вот тут вообще какой-то `Pin<Box>`... Спасибо, что не Pinhead...   

Его во всех источниках объясняют максимально сложно, туманно, как будто бы это что-то очень фундаментально важное и не каждому дано понять. А чтоб максимально всех запутать, использовали терминологию с отрицанием и двойным отрицанием... Худший выбор именования.

Потому я поставлю себе здесь задачу объяснить просто. Но длинно.

## Нырнем в прекрасный чистый C

В прекрасном чистом C мы можем создавать прекрасные чистые пользовательские структуры.

```C
typedef struct {
    int x;
    int y;
} Pair;
```
И любую стурктуру, если мы знаем ее определение [^1], можно скопировать. **Что бы в ней ни находилось**
А также ее можно передать по значению в функцию. Или вернуть обратно из нее.

*В C все типы копируемые*

```C
Pair foo(Pair x) {
    // сколько хочу, столько и копирую
    Pair y = x;
    Pair z = x;
    return z;
} 
```



В прекрасном чистом C есть также прекрасные указатели. Которые можно брать на все что угодно. А еще их можно также сохранять куда угодно.

```C
typedef struct {
    int buffer[1024];
    // read_ptr будет ссылаться на buffer
    const int* read_ptr;
} IBuffer;

void initialize_buffer(IBuffer* r) {
    // заполняем буфер чем-то
    // fill(r->buffer, ....)
    // и выставляем указатель на его начало, для чтения
    r->read_ptr = r->buffer;
}

int read_one(IBuffer* r) {
    int val = *(r->read_ptr);
    r->read_ptr++;
    return val;
} 
```

Вот дал вам кто-то библиотеку с такой структурой и методами и сказал:

- Пользуйся вот так, и будет хорошо

```C
void example_buffer() {
    IBuffer buf;
    initialize_buffer(&buf);
    int val = read_one(&buf);
    // делай с val что хочешь
}
```

Пришел потом какой-нибудь непуганный энтузиаст, искуственный иль органический, взглянул на это, не посмотрев в библиотеку, и сделал красиво

```C

IBuffer make_buffer() {
    IBuffer buf;
    initialize_buffer(&buf);
    return buf;
}


void example_buffer() {
    IBuffer buf = make_buffer();
    int val = read_one(&buf);
}
```

Запустил, довольный, и получил черт знает что, а не значение из буфера.

Так он познакомился со структурами, которые ссылаются сами на себя.

```C
IBuffer buf;
initialize_buffer(&buf);

// buf->read_ptr указывает на buf->buffer;
// buf->read_ptr == buf->buffer. П

IBuffer another_buffer = buf;
// another_buffer->read_ptr все также указывает на buf->buffer!
// another_buffer->read_ptr != another_buffer->buffer

// Если считать объект IBuffer самодостаточной абстрактной коробкой, 
// у нее оказывается изменяются свойства при копировании.
// И меняются нежелательным образом -- коробка оказывается сломанной
// 
```

И так он понял, несмотря на то что в C все структуры можно копировать, некоторые структуры копировать точно не стоит! [^2].

Наученный на своем опыте, стал он думать, а как же нам избежать неправильного использования. Ведь наверняка же кто-то, как и он, возьмет да и скопирует структуру IBuffer! Не все же [^3] читают документацию и комментарии в коде!

И придумал он следующее решение

Надо сделать недоступной саму структуру IBuffer, а разрешить пользоваться только указателями на нее.

Но не было в прекрасном чистом C адекватного способа осуществить задуманное. Разве что породить макрос чудовищный

```C
#define MAKE_IBUFFER(name) \
    IBuffer IBUFFER_hidden_##name; \
    IBuffer* name = &IBUFFER_hidden_##name; initialize_buffer(name);  
```

И сказать:
- Пользуйтесь так, и будет хорошо

```C
void example() {
    // buf -- это IBuffer*
    MAKE_IBUFFER(buf);
    read_one(buf);
}
```

Но пришел затем глупец еще более непуганный и сделал

```C
IBuffer example() {
    MAKE_IBUFFER(buf);
    read_one(buf);
    // могу копировать что угодно 
    // в чистом прекрасном C!
    return *buf;
}
```
Чтоб глупец так больше не делал, можно, например, убрать определение типа IBuffer из публичных заголовков, а в `MAKE_IBUFFER` создавать анонимый тип совместимый по структуре с `IBuffer`... Но это все костыли поверх костылей, которые не нужны для нашей истории. 

## С++ решит все проблемы

В C++ есть конструкторы. В частности конструкторы копирования и перемещения. А еще их можно удалять или делать приватными.
Объект с удаленным/приватным конструктором копирования/перемещения нельзя скопировать или переместить. Проблема решена.

```C++

class IBuffer {
public:
    IBuffer() = default;

    // Запрещаем копирование и перемещение
    IBuffer(const IBuffer&) = delete;
    IBuffer(IBuffer&&) = delete;
    IBuffer& operator = (const IBuffer&) = delete;
    IBuffer& operator = (IBuffer&&) = delete;

    int read() {
        int val = *read_ptr;
        read_ptr++;
        return val;
    }

private:
    int buffer[1024];
    // О как можно!
    int* read_ptr = buffer;
};
```

Все. И ни один непуганный глупец не сможет сделать так

```C++
void example() {
    IBuffer buf;
    IBuffer another = buf; // ошибка компиляции
    // error: use of deleted function 'IBuffer::IBuffer(const IBuffer&)'
}
```

Как хорошо когда в системе типов есть неперемещаемые и некопируемые типы. А также любая комбинация: например, копируемый, но неперемещаемый. Или перемещаемый, но не копируемый.

Удобно!

## А теперь снова к крабам

*В Rust все типы перемещаемые.* А еще в Rust есть указатели. Сырые и небезопасные. Но их можно безопасно брать и сохранять куда угодно.
Ничего не напоминает?
Ровно та же самая проблема как и в C. Только вместо копирования перемещение

```Rust
struct IBuffer {
    buffer: [i32; 1024],
    read_ptr: *mut i32,
}

impl IBuffer {
    fn new() -> Self {
        Self {
            buffer: [0;_],
            read_ptr: std::ptr::null_mut(),
        }
    }
    fn initialize(&mut self) {
        // совершенно безопасно
        self.read_ptr = self.buffer.as_mut_ptr();
    }
}

fn example() {
    let mut buf = IBuffer::new();
    buf.initialize()

    // могу переместить в новую переменную
    let mut another_buf = buf;
    assert!(another_buf.read_ptr == another_buf.buffer.as_mut_ptr());
    // assertion failed: another_buf.read_ptr == another_buf.buffer.as_mut_ptr()
}
```
Понятное дело, для разыменования указателя в любом случае нужен будет `unsafe {}`.
Но хочется же его как-то завернуть в безопасные функции. А то чем мы лучше чем C?!

Что ж делать-то!? 
Раз уж у нас все типы перемещаемые, то надо просто запретить by-value доступ к созданному `IBuffer`.
Оставить только доступ по ссылке.

Но в Rust нет адекватного способа добиться желаемого! Разве что придумать чудовищный макрос (кажется, у меня Дежавю)

```Rust

macro_rules! make_ibuffer{
    ($name:ident) => {
        let mut $name = IBuffer::new();
        // Зато в Rust есть затенение имен, так что только
        // к ссылке будет доступ
        let $name = &mut $name;
        $name.initialize();
    }
}

```

```Rust

fn example() {
     make_ibuffer!(buf);
     // buf -- это &mut IBuffer
     let another_buf = *buf; // ошибка компиляции! Ура!
}

```

Отлично, спасибо, что в Rust по умолчанию пользовательские типы не копируемые. Их надо явно помечать как копируемые.

Все? Проблема решена? Да, корявенько, как в C, но чуть лучше. Решена же? Можно писать безопасный метод `fn read_one(&mut self)` и радоваться?

Ха! Нет. Ведь *в Rust все типы перемещаемые*, а это не только значит, что всегда можно сделать `let a = b;` Но и, самое главное, -- поменять местами два значения. Не создать новые переменные, а обменять значения старых.

```Rust
fn swap_ibuffer(a: &mut IBuffer, b: &mut IBuffer) {
    std::mem::swap(a, b);
}

fn example() {
     make_ibuffer!(buf_a);
     make_ibuffer!(buf_b);
     swap_ibuffer(buf_a, buf_b);
     // ой, упало
     assert!(buf_a.read_ptr == buf_a.buffer.as_mut_ptr());
}
```

Надо было писать на C++... Но обратного пути нет. Надо идти до конца.

Мы с помощью макросни скрыли доступ by-value. Это победа.
Теперь оказывается что и доступ к `&mut` ссылке тоже надо обрубить, чтоб никакой глупец не сделал `std::mem::swap`.

И тут, из соображений backward compatibility стандартной библиотеки и языка в целом [^4], вместо радикального решения - ну давайте серьезно сделаем просто unmovable типы - сумрачный гений родил невероятно костыльное решение.

### Шаг первый. Еще один тип ссылок

Чтоб не было проблемы с доспупом к `&mut` ссылке, надо просто сделать этот доступ небезопасным. Тогда проблема будет на стороне `unsafe {}` кода, и никакой глупец в safe коде себе ногу не отпилит.

Берем и оборачиваем ссылку (указатель, для общности) в спец обертку, которую и назовем `Pin`

```Rust
struct Pin<Pointer>(Pointer);

impl<'a, T: ?Sized> Pin<&'a mut T> {
    // Создавать такие ссылки будет небезопасно
    unsafe fn new_unchecked(p: &'a mut T) -> Self {
        Self(p)
    }
    // И доставать из них обычную ссылку -- тоже
    unsafe fn get_unchecked_mut(self) -> &'a mut T {
        self.0
    }

    // для перезаимствования
    fn as_mut<'b>(&'b mut self) -> Pin<&'b mut T> {
        Self(self.0)
    } 
}
```

И теперь, вооружившись таким новым модным типом ссылок, который защитит safe код от беспощадного `std::mem::swap`, мы можем сделать безопасный интерфейс для нашей злосчастной структуры

```rust
struct IBuffer {
    buffer: [i32; 1024],
    read_ptr: *mut i32,
}

impl IBuffer {
    fn new() -> Self {
        Self {
            buffer: [0;_],
            read_ptr: std::ptr::null_mut(),
        }
    }
    // После инициализации доступ становится небезопасным
    fn initialize(&mut self) -> Pin<&mut Self> {
        // совершенно безопасно
        self.read_ptr = self.buffer.as_mut_ptr();
        unsafe { Pin::new_unchecked(self) }
    }


    fn read_one(self: Pin<&mut Self>) -> Option<i32> {
        // Ага, мы работает с особой ссылкой, 
        // которая самим фактом своего существования говорит,
        // что наше самореферентное состояние корреткно --
        // ссылка получена из initialize().
        //
        // А если каким-то другим путем через unsafe {}
        // со стороны пользователя, то вся вина за ошибку памяти на нем
        //
        let this = unsafe { self.get_unchecked_mut() };
        if unsafe { this.read_ptr.offset_from(this.buffer.as_ptr()) == this.buffer.len() as isize } {
            return None;
        }
        let val = unsafe { *this.read_ptr };
        unsafe { this.read_ptr.add(1) };
        Some(val)
    }
}

```

Все, отлично, проблема решена! Можно на этом остановиться...

Нет! Нужно обобщенное решение! Ведь есть много разных типов указателей. `Box<T>`, например. А еще для консистентности надо просто `&` ссылки поддержать...

Как это делать -- понятно и прямолинейно. Берем и реализуем `impl Pin<&T>`, `impl<P: Deref> Pin<P>`, `impl<P: DerefMut> Pin<P>`.

Все? Погодите...

### Шаг второй. Unmovable типы у нас все-таки будут.

Что если кому-то очень надо работать с `Pin<&mut T>` где `T` -- совершенно обычный Rust тип, без всей этой самореферентной ерунды. Вот было бы здорово, чтоб `Pin<&mut T>` был тогда как будто бы всего лишь алиасом для `&mut T`. И никакого unsafe не надо было бы. 

Как такое может вообще случиться? Ну, скажем, переусердствовали мы с generic интерфейсом -- публичным типажем `trait Foo`, засунули в него `self: Pin<&mut Self>` везде, а у каждого второго вменяемого пользователя, типы не требуют никаких гарантий неперемещаемости. Что ж им теперь, везде unsafe {} писать, при реализации `impl Foo for MyType`? А вдруг у них паранойа? Не, так не пойдет. Нужна фича, чтоб `Pin<&mut T>` был как `&mut T`, если это безопасно.

Что ж... Поехали!

В Rust есть типажи. Давайте введем специальный типаж, сродни `Copy`, который бы говорил, что объекты этого типа можно перемещать.
И назовем его... нет не `Movable`, как могли бы подумать многие, а `Unpin`.
А типы, которые его не реализуют, то есть те самые интересные типы, небезопасные к перемещению, будут  `!Unpin` -- `NotUnpin`. С двойным отрицанием. Чтоб никто не запутался.

Далее я буду писать `Movable` и `Pinned`, потому что использование `Unpin` и `!Unpin` в примерах кода -- настоящее издевательство и перенапряжение внимания, которое не помогает пониманию.

```
 Movable   ==  Unpin
 Pinned    == !Unpin
```

Отлично. Типаж введен. Добавляем запрошенную фичу с его помощью

```rust 
impl<P: Deref> Deref for Pin<P>
{
    type Target = P::Target;
    fn deref(&self) -> &Self::Target {
        self.0.deref()
    } 
}

impl<P> DerefMut for Pin<P>
where P: DerefMut<Target : Movable> 
{
    fn deref_mut(&mut self) -> &mut Self::Target {
        self.0.deref_mut()
    }
}
```

Также можно добавить безопасный конструктор

```rust
impl <P> Pin<P> 
where P: Deref<Target: Movable> 
{
    fn new(p: P) -> Self { Self(p) }
}
```


Теперь, для безопасных типов `T`, можно будет присваивать значения и в целом добираться до `&mut T` без unsafe.

Осталось теперь только научиться помечать плохие типы как неперемещаемые, чтоб для них продолжал требоваться unsafe.

В Rust умолчанию все `Movable`. И любая структура, у которой все поля `Movable` тоже `Movable`. [^5]
Чтобы все-таки пометить свой тип как небезопасный для перемещения, то есть `Pinned`, в стандартную библиотеку добавили тип-маркер `std::marker::PhantomPinned`. Который реализует `Pinned`.

```rust

struct IBuffer {
    buffer: [i32; 1024],
    read_ptr: *mut i32,
    pinned: std::marker::PhantomPinned, 
}

```

### Шаг третий. Делаем универсальную макросню

Метод инициализации
```Rust
impl IBuffer {
  fn initialize(&mut self) -> Pin<&mut Self> {
    // совершенно безопасно
    // устанавливаем самореферентное свойство
    self.read_ptr = self.buffer.as_mut_ptr();
    unsafe { Pin::new_unchecked(self) }
  }
}
```
Очень удобно избавляет от необходимости возиться с макросами.

Но в общем случае паттерн работы с самореферентными типами выглядит так

```Rust
   let mut object = create(....);
   // гарантируй что object никуда больше не переместят (1)
   object.method1();
   object.method2();
   ... 
   // и все эти методы принимают Pin<&mut Self>
```
И как раз-таки это "гарантируй что объект никуда не переместят" может быть достигнуто одним из двух способов

1. Выделить память в куче (`Box<Object>`) и заверни полученный указатель (`Box`) в обертку (`Pin<Box<Object>>`)
2. Как мы делали раньше -- спрячь by-value доступ к объекту на стеке.

Второй способ, как и раньше, выполняется с помошью макроса. Его простейшая вариация:

```Rust
macro_rules! pin {
    ($name:ident) => {
        // перекрываем исходное имя переменной, чтоб она стала недоступной
        let mut $name = Pin::new_unchecked(&mut $name);
    }
}
```
В стандартной библиотеке Rust этот макрос более сложный, использует unstable фичи, и позволяет передавать в него не только имя переменной, но и произвольные выражения.

----------

## Итого

1. `Pin<Pointer>` -- это всего лишь костыль, чтоб в safe коде нельзя было добраться до `&mut T` ссылки, если `T` может сломаться от перемещения (например, через `std::mem:swap`)[^6]
2. `Unpin` -- это просто `Movable`. Все нормальные перемещаемые типы.
3. Наслаждаемся невероятными решениями для поддержания обратной совместимости




----------


[^1]: Самое главное -- знать размер и требования к выравниванию. В compile time мы их знаем только если определение типа находится у нас в области видимости. 
[^2]: Точнее, не стоит трогать полученные копии. Они радиоактивные.
[^3]: AI читает. Но тоже не всегда следует.
[^4]: Мы, например, можем спокойно вызвать методы крейтов c Rust edition = 2018 в новых крейтах с edition == 2024.
[^5]: На этом магия компилятора заканчивается. В остальном можно построить свои собственные `Movable`, `Pinned` и `Pin` также как было рассмотрено на примере `Send` и `Sync`
[^6]: Примечательное применение `Pin<&mut Type>`, можно обнаружить при использовании крейта `cxx` для генерации ffi переходников между Rust и C++. Для любой импортируемой C++ функции с сигнатурой `CppType& foo(args)` на стороне Rust нужно использовать `fn foo(args) -> Pin<&mut CppType>`. `CppType` может быть и не имеет никаких ссылок на самого себя внутри. Но корректное перемещение C++ типов требует вызова конструктора перемещения. О котором Rust ничего не знает. Так что давать доступ к `&mut CppType` нельзя -- а то вдруг какой-то умник `std::mem::swap` вызовет
