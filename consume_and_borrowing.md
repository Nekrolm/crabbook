# (дис)функциональный стиль

Не секрет, что Rust взял очень многое от функциональных языков программирования. Его синтаксис в принципе был вдохновлен OCaml'ом [^1].

Rust, со всем его фокусом вокруг владения, его передачи, и ограничения заимствований, во многом подталкивет разработчиков предерживаться функционального подхода. Я б хотел сказать, что Rust его поощряет, но тут скорее он просто больше наказывает за использование других, привычных многим, паттернов и подходов:
- Поменьше мутабельности -- за неосторожные и наивные попытки раздавать `&mut` ссылки вас накажет компилятор
- Поменьше ссылок -- вы будете платить за них протаскиванием lifetime-параметров
- Четко разделяйте данные и операции над ними -- за попытки запихнуть все в один объект и вызывать на нем методы вас накажут 

И многое другое.

Как-то один самоуверенный C++-разработчик отметил, что в Rust ничего сложного нет, просто надо принять, что это функциональный язык и "перестать выделываться". В частности, он дал рецепт: надо просто все `fn foo(x: &mut T)` писать как `fn foo(x: T) -> T`. Они ж эквивалентны. И всё будет классно.

Ну действительно. Чисто синтаксически все будет классно: никаких больше ссылок. Все иммутабельно. Если что, просто копию сделаем. Ленивую. А компилятор уже все эффективно сделает. Он же умный. Там же ого-го какая семантика перемещения с аффинными типами-то!

Давайте посмотрим.

```Rust
// Действительно, превратить

fn foo_mut(x: &mut T) {...}

// в

fn foo(x: T) -> T {
    // можно очень просто
    let mut x = x;
    foo_mut(&mut x);
    x;
}

// или короче

fn foo(mut x: T) -> T {
    foo_mut(&mut x);
    x;
}
```

Но стоит ли так делать всегда и везде?

Пойдем издалека.

C++ за многие годы прошел очень долгий и тяжелый путь в попытках гарантировать отсутствие избыточных копий при передаче/возравщении объектов из функций -- (named)return-value оптимизации ((N)RVO).

```C++
std::string foo() {
    std::string tmp = "helloloooooooongstring";
    // В очень старых версиях C++, вот здесь происходило копирование:
    // аллокация новой памяти, деллокация старой
    // 
    // В современных версиях C++, гарантируется, что не только не будет копирования (C++ copy-ctor) или перемещения (С++ move-ctor), но и в принципе, даже тривиально байтики дополнительно не будет переложены!
    // tmp создан и заполнен прямо в return-слоте в стэк-фрейме вызывающей стороны!
    //
    // Это максимально близко к поведению destructive move, существующему в Rust
    return tmp;
}

// можно сказать, что foo "переписывается" (при компиляции) в
void foo(void* ret_slot) {
    std::string& tmp = *(new(ret_slot) std::string("helloloooooooongstring"));
    // нужны дополнительные действия для вызова деструктора в случае исключения
}
```

К сожалению, никаких гарантий нет, и не может быть, в случае, если переменная -- это аргумент функции.

```C++
std::string foo(std::string x) {
    x.append("extra hello");
    // неизбежна копия/перемещение -- выполнение C++ конструктора (copy или move). 
    // Необходимо создать новый объект, а старый уничтожить, вызвав деструктор x
    // в конкретном случае, С++17 и новее вставит move-конструктор
    return x;
}


// функция никогда не будет автоматическа переписана в виде
// Ведь компилятор не может делать таких лихих предположений о локации входных и выходных параметров
void foo(std::string& x) {
    x.append("extra hello");
}

...

std::string s;
// никак не может быть слот под s использоваться
// так же и под временны аргумент
// разве что если foo полностью заинлайнена здесь
s = foo("hello"); 

```

Для C++, когда конкретная мономорфизированная (не шаблонная) функция объявлена (и ее объявление может быть предоставлено для независимой компиляции других единиц трансляции) -- конвенция вызова для нее должна быть определена и зафиксирована: не может быть для одних случаев один in-out указатель, а для других: in отдельно, out отдельно.

Вернемся к Rust.

- В Rust же у нас есть гарантированная деструктивная семантика перемещения

```Rust
fn foo(mut s: String) -> String {
    s.push_str("extra hello");
    // не будут вызваны никакие деструкторы для s
    // s, как объект (1 указатель и 2 числа: data, len, capacity), будет просто побитово перемещен из входного слота в выходной.
    s
}
```

Здорово. Проблем нет, да?

Давайте посмотрим на чуть более сложный пример. Возьмем объектик побольше!

```rust

use std::ffi::c_void;
use std::ptr::NonNull;

#[derive(Copy, Clone)]
pub struct MyState {
    buffer: [u8; 1024],
    callback: fn(buffer: &mut [u8], context: NonNull<c_void>),
    context: NonNull<c_void>,
} 

// Чтоб слишком умный компилятор не выбросил целиком весь наш код
// функция будет обращаться к некоторому неизвестному указаетлю на неизвестную функцию
// довольно стандартная ситуация
fn evolve_mut(s: &mut MyState) {
    (s.callback)(&mut s.buffer, s.context);
}


#[inline(never)]
pub fn test_iter_mut(mut s: MyState, n: usize) {
    for _ in 0..n {
        evolve_mut(&mut s);
    }
}


```

Но как же! Как же! Компилятор Rust же умный... И у нас никакой раздельной компиляций, если есть зависимости между крейтами. Все строго по очереди... Да еще и прямо заинлайнено же! Почему же нам наделали перекладываний байтов туда-обратно, когда очевидно же, что их можно избежать?!

Точно так же как и в случае C++, копилятор Rust не вправе переписать

```Rust
fn evolve(mut s: MyState) -> MyState {
    evolve_mut(&mut s);
    s
}
```
обратно в `fn evolve_mut(s: &mut MyState)` и использовать в таком виде. Вообще компиляторы не вправе переписывать код так, чтобы у него поменялась семантика [^3]. 

Даже без оглядки на вопросы фиксирования конвенции вызовов:
В Rust, как и в C++, есть механизм аварийной раскрутки стека -- для паник (исключений). 

Если `evolve_mut(&mut s)` паникует где-то в процессе модификации `s`, объект может быть изменен, частично или полностью! 

Если же в `s = evolve(s)` случится паника. То `s` изменен не будет. Он либо останется оригинальным (будучи `Copy`). Либо станет `moved out` -- и там уже не важно, ведь если скомпилировалось, значит, к нему больше не обращаются. 


Так надо просто поймать панику!

Увы, это не поможет. Rustc не выполняет такую оптимизацию. Возможно, в будущем. Но не сейчас.

Вернемся теперь обратно к нашему "эквивалентному преобразованию". А что если мы хотим обратно, перейти к `fn foo_mut(x: &mut T)`, имея лишь `fn foo(x: T) -> T`? 

Элементарно! Немножко `unsafe {}`:

```rust

// https://docs.rs/take_mut/latest/take_mut/

#[inline(always)]
pub fn take<T, F>(mut_ref: &mut T, closure: F)
  where F: FnOnce(T) -> T {
    use std::ptr;
    unsafe {
        // Насильно делаем битовую копию
        let old_t = ptr::read(mut_ref);
        let new_t = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| closure(old_t)))
        // Нет спсособа безопасно восстановиться: на скопированном объекте был вызван деструктор. 
        // Нельзя допустить вызова деструктора на оригинальном объекте -- будет double free
        // Умираем
            .unwrap_or_else(|_| ::std::process::abort());
        // Иначе все ок:
        // Переписываем поверх, не вызывая деструктор!
        ptr::write(mut_ref, new_t);
    }
}
```

Применим теперь эту замечательную функцию к нашей тестовой структуре

```Rust
#[inline(always)]
fn evolve_mut2(s: &mut MyState) {
    take(s, evolve)
}


#[inline(never)]
pub fn test_iter_mut2(mut s: MyState, n: usize) {
    for _ in 0..n {
```

-------------

В Rust эти чистые и красивые функции `fn foo(T) -> S<T>` так хороши для выражения статически проверяемых переходов между состояниями. Например, можно сделать чудесный итератор, который точно никогда не будут использовать после завершения итераций:

```Rust

trait Iterator {
    type Item;
    fn next(self) -> Option<(Self::Item, Self)>;
}
```

Но для хоть сколько-нибудь больших структур (больше нескольких указателей) пенальти накладных расходов но постоянное перекладываение байтов становится существенным. Ужасные и грязные `fn foo(&mut T) -> S` более предпочтительны, если вам необходима гарантированная производительность и гарантированные inplace манипуляции. 
Особенно для inplace конструирования новых объектов -- тут Rust пока очень сильно проигрывает C++: В C++ есть гарантированный placement new. А в Rust его нет. Подробнее об этом в следующей части.
