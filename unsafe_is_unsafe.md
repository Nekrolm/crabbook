# In Rust We Trust, или почему unsafe {} это unsafe

Очень многие, попробовавшие программировать на Rust, отмечают, что чаще всего, если их код скомпилировался, то он работает из коробки и не упадет. И требуется лишь минимальное тестирование ожидаемого поведения, чтоб отловить логические ошибки. Также в больших проектах на Rust редко приходится думать, как локальное изменение в одном месте может повлиять на остальную кодовую базу. 

Это не просто совпадение, а следствие важного выбора при дизайне языка: упор на local reasoning [^1]:
- Ограничения safe языка таковы, что любая safe комбинация safe функций остается safe. Этому значительно способствует семантика передачи владения, а также жесткое разграничение на уникальные-мутабельные и разделяемые-константные ссылки
- Borrow checker анализирует каждую функцию по-отдельности, а не всю кодовую базу целиком. Для этого и нужны аннотации времен жизни, статическая типизация, обязательное указание типажей.

Можно очень легко привести пример на С++, в котором комбинация двух совершенно безопасных по отдельности функций становится небезопасной


```C++
struct Task {
    void run() {}
};

struct Processor {
    // совершенно безопасно
    void spawn_task(Task&& new_task) {
        this->tasks.push_back(std::move(new_task));
    }

    // тоже совершенно безопасно
    void process_tasks(std::invocable<> auto on_each_completion) {

        for (auto& task: this->tasks) {
            task.run();
            on_each_completion();
        }

    }

    std::vector<Task> tasks;

};


void run_processor(Processor& p) {
    // бум! реаллокация вектора из-за добавления новых задач сломает итераторы 
    // цикла в process_task
    p.process_tasks(
        [&p]{
            p.spawn_task(Task{});
        }
    );
}
```



В Rust такая комбинация просто не проедет провеку borrow checkerа

```rust
struct Task;
impl Task {
    fn run(&mut self) {}
}

struct Processor {
    tasks: Vec<Task>
}

impl Processor {
    fn spawn_task(&mut self, t: Task) { self.tasks.push(t); }
    fn process_tasks(&mut self, mut on_each_completion: impl FnMut()) {
        for t in self.tasks.iter_mut() {
            t.run();
            on_each_completion();
        }
    }
}


fn run_processor(p: &mut Processor){
    p.process_tasks(|| {
        p.spawn_task(Task);
    });
}
```

```
error[E0501]: cannot borrow `*p` as mutable because previous closure requires unique access
  --> src/lib.rs:23:5
   |
23 |       p.process_tasks(|| {
   |       ^ ------------- -- closure construction occurs here
   |       | |
   |  _____| first borrow later used by call
   | |
24 | |         p.spawn_task(Task);
   | |         - first borrow occurs due to use of `*p` in closure
25 | |     });
   | |______^ second borrow occurs here
```

Обратите внимание, что компилятор в ошибке не рассказывает никаких внутренних деталей: это неправильно, потому что вот там внутри вектор реаллоцируется. Он сообщает только информацию, которую взял из сигнатур функций: здесь требуется мутабельный доступ и тут требуется мутабельный доступ.


В Rust безопасные функции могут доверять другим безопасным функциям. И не только лишь в непросредственном обращении с памятью. В Rust многие типы обещают дополнительные инварианты и на эти инварианты полагается компилятор выполняя те или иные оптимизации. Например, если `x: NonZero<i32>`, то для `1000 / x.get()` не нужно генерировать отдельные инструкции для паники при делении на 0. Или размер `Option<&str>` гарантировано совпадает с `&str`, потому что ссылки не бывают нулевыми, а значит нулевой bit-паттерн можно использовать для представления `None`.

И весь этот прекрасный мир взаимного доверия очень легко разрушить с помощью одного `unsafe {}`.

Однажды, я увидел следующие несколько строчек на одном из горячих путей обработки запросов

```rust

let encoded_logs = logs
             .replace("\n", "\\n")
             .replace("\t", "\\t")
             .replace("\r", "\\r");
```
`str::replace` берет ссылку на строку и создает новую строку... Это целых три аллокации!
Логи могли быть довольно длинными -- по 10KB -- аллоцировать трижды по три страницы...

Разумно сделать как-то так

```rust
let mut encoded_logs = String::with_capacity(logs.len() * 2); // в худшем случае каждый символ превращается в 2
for c in logs.chars() {
    match c {
        '\n' => encoded_logs.push_str("\\n"),
        '\t' => encoded_logs.push_str("\\t"),
        '\r' => encoded_logs.push_str("\\r"),
        c    => encoded_logs.push(c)
    }
}
```

Преобразование эквивалентно иходному, поведение сохранено, тесты пройдены, метрика производительности в среднем улучшилась (20 потоков стали меньше ломиться в глобальный аллокатор) -- можно заливать в release билд.

Через пару недель в одной из локаций сервис падает с паникой... И трейс указывает именно на этот измененный участок!
Что пошло не так?!

Оказывается, эти логи через множество промежуточных функций приходят из IPC сообщения представленного как flatbuffer. И доступ к полю `logs` внутри flatbuffers библиотеки выглядит так[^3]
```rust
    unsafe { str::from_utf8_uchecked(str_bytes) }
```
У Rust-строк (String и str) есть важный инвариант -- они обязаны быть представлены корректными UTF-8 последовательностями. И любой unsafe код создания и манипуляции строками должен уважать этот инвариант.

Строки в flatbuffer сообщении были созданы C++-приложением. А C++ никого не уважает. Поэтому в редких случаях, в зависимости от действий пользователя, в логи могли попасть не utf-8 последовательности. И инвариант мог быть нарушен.

**Один unsafe в сторонней библиотеке ломает свойство локальности изменений в сервисе**

`str::replace` (со строковым аргументом - это важно!) в таких условиях продолжает работать и скрывать проблему: строковое сравнение [^2] для utf-8 строк это просто побайтовое сравнение, никаких дополнительных требований.

`str::chars()` же вычленяет каждый utf code-point по отдельности из utf-8 последовательности и, слепо доверяя обещанным инваринатам, может взять и обратиться к несуществующему элементу где-то [тут](https://doc.rust-lang.org/src/core/str/validations.rs.html#48)


-----------------------------------

[^1]: Как обычно бывает, в async Rust все сложнее и local reasoning перестает работать. Но не из-за асинхронности как таковой. Borrow сhecker работает с сигнатурами функций, а сигнатура `async fn foo(args: Args) -> Bar { ... }` на самом деле `fn foo(args: Args) -> impl Future<Output = Bar> + use<Args> { ... }` и что мы дополнительно напишем в теле функции может поменять тип возравщенной `impl Future`, тем самым сломав (во время компиляции) код где-нибудь в совершенно другом модуле. Самый распространенный пример: на одном краю проекта сидит `tokio::spawn(my_function())`, а на другом краю вы добавили какой-нибудь `!Send` объект в тело функции `async fn foo()` и не удалили его перед `.await` -> бах и через всю цепочку вызовов компилятор засыпает вам ошибками, что `tokio::spawn` требует `F: Send`, а у вас что-то `!Send`.
Кстати, это справедливо не только для async функций, но и для любых, использующих `impl Trait` в возвращаемой позиции.

[^2]: Не учитывающее unicode нормализацию, разумеется. 

[^3]: Версия библиотеки flatbuffers была довольно старой и там не было поддержки валидации сообщений. В наиболее свежих версиях при вызове `flatbuffers::root::<MyMessage>(bytes)` возвращается `Result<MyMessage, ValidationError>`. И не utf-8 строки внутри сообщения приведут к ошибке как и ожидается. Просто обновить библиотеку и дело с концом?! Увы, это breaking change для сервиса: ведь ошибка отбраковывает все сообщение, а не только лишь поломанные логи внутри него.
